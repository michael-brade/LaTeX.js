Developing LaTeX.js ​

This page is about working on LaTeX.js itself: setting up the repository, building and testing it, the website, and the conventions of the code. To add macros, document classes or packages, see Extending.

LaTeX.js is written in TypeScript. The parser is generated from a PEG grammar by peggy, the library and the CLI are built with Vite, the tests run with Vitest, and the website, including the playground, is built with VitePress.

Setup ​

You need Node.js 22 or newer (the CI uses Node.js 24) and rsync, which the build uses. Regenerating package.json (see below) also needs sponge from moreutils. The dev container in .devcontainer/ has all of this, including the libraries that Chrome and Firefox need for the screenshot tests.

sh
git clone https://github.com/michael-brade/LaTeX.js.git
cd LaTeX.js
npm install
npx puppeteer browsers install    # once if it didn't happen automatically: Chrome/Firefox for screenshot tests
npm run build
npm test

Commands ​

sh
npm run build        # library → dist/ (vite.config.ts), CLI → bin/latex.js (vite.cli.config.ts), css/fonts/js → dist/
npm run devbuild     # same, unminified, no source maps
npm run typecheck    # tsc for src/, test/, and docs/.vitepress/ (including the .vue files)
npm test             # vitest run
npm run testc        # vitest run --coverage, report in test/coverage/; needs `npm run build`, not devbuild: source maps
npm run test-int     # integration tests: npm pack tarball installed into consumer projects (needs a build)
npm run devdocs      # `vitepress dev docs` (needs a build)
npm run docs         # build + generate the website into the gh-pages worktree ./website and commit it there
npm run clean        # remove the build output, test/coverage/, the VitePress cache and the website/ worktree

The tests and the website use the built library from dist/ and bin/, so build first.

The generator and the macros use TC39 decorators; Babel transpiles them in the Vite build.

Tests ​

npm test runs all tests. To run only some of them, pass files or a filter, e.g. npx vitest run test/cli.test.ts; the Vitest extension for VS Code runs and debugs single tests. DEBUG=chrome npm test (or DEBUG=firefox) shows that browser with its devtools instead of running it headless.

  • test/fixtures.test.ts translates the fixtures and compares the HTML,
  • test/cli.test.ts runs bin/latex.js,
  • test/api.test.ts runs the examples in test/api/: the Node examples with node, the browser example in Chrome, and it takes screenshots of the web component examples.

Fixtures ​

The files in test/fixtures/ (and its subdirectories) contain fixtures: a title, the LaTeX source and the expected HTML, each followed by a line with a single .:

paragraphs and newlines
.
first line\\second line\newline third line\par and then a new paragraph as well
.
<div class="body">
<p>ﬁrst line<br>second line<br>third line</p>
<p>and then a new paragraph as well</p>
</div>
.

A line with attributes may come before the title: ! skips the fixture, + runs only the fixtures that have it, and # also takes screenshots of it. The fixtures are translated without hyphenation; line breaks in the HTML are ignored. When a fixture fails, its actual HTML is written to test/html/.

Screenshots ​

The fixtures with # and the web component examples are rendered in Chrome and Firefox (with puppeteer) and compared with the screenshots in test/screenshots/ (.ch.png for Chrome, .ff.png for Firefox) using BlazeDiff. If there is no stored screenshot yet, the new one is stored. If they differ, the new screenshot is written next to the stored one as .new.png, and the difference as .diff.png (pixels that got darker are green, lighter ones red). If the change is intended, replace the .png with the .new.png; don't commit the .new.png and .diff.png files.

Coverage ​

npm run testc writes a coverage report to test/coverage/ (open index.html). It needs npm run build: the tests run the bundles in dist/ and bin/, and only their source maps lead back to src/. After a devbuild, the coverage is 0%.

Integration Tests ​

npm run test-int needs a build and network access. It tests the package the way consumers get it:

  • test/integration/pack.sh creates the tarball test/integration/tmp/latex.js.tgz with npm pack,
  • consumer.sh installs it into a new project and runs the Node API examples and the CLI there; it also type-checks a consumer with strict and without skipLibCheck: an ES module consumer with the module resolutions bundler, node16 and nodenext, and a CommonJS consumer with node16 and nodenext,
  • react.sh builds a Vite + React app that uses the package and checks in Chrome that it renders. The app stays in test/integration/react-app/, so you can try it with npm run dev there.

Run them when you change the build or the public API: npm run build && npm run test-int.

Website and Playground ​

npm run devdocs starts the VitePress dev server; the playground is at /playground and compiles LaTeX live into an iframe. In the pages, <latex/> and <tex/> render the logos, and the library examples in Usage are included from test/api/ (with <<<), so they are tested.

The website uses the library from dist/: "latex.js" resolves through exports, and docs/public/latexjs/{css,fonts,js} are committed symlinks to dist/{css,fonts,js} (the playground loads them from /latexjs/; vitepress build copies the real files). After changes in src/, rebuild (npm run devbuild is faster) and restart devdocs; for changes of the CSS, fonts or scripts, a rebuild is enough.

npm run docs builds the library and then the website into website/, a worktree of the gh-pages branch (created if it doesn't exist), and commits it there. It doesn't push.

package.json ​

package.json is generated, so never edit it by hand. The source of truth is the YAML in package.yaml.sh: edit that file, then run ./package.yaml.sh (it pipes the YAML through npx js-yaml into package.json), then npm i. Commit package.yaml.sh, the regenerated package.json and package-lock.json together.

  • The YAML in package.yaml.sh is a quoted heredoc (<<'EOF'), so it is passed to js-yaml verbatim: $ in scripts needs no escaping.
  • Chain script steps with &&, not ;, so a failing step stops the script.
  • Every script must end with ; (a lone ; after the last command). npm appends the arguments of npm run <script> <args> to the script's command line. Without the ; they would extend the last command: npm run clean / would run rimraf … /. With it, they become a separate command, which fails harmlessly. Keep the ; when adding or editing scripts, including one-liners (test: vitest run;).
  • prepare runs patch-package (the patches are in patches/). It is prepare, not postinstall: prepare runs on npm install/npm ci in this repository, but not when latex.js is installed as a dependency, where postinstall would run and fail (it needs devDependencies).

Dependencies ​

  • The libraries that Vite bundles into dist/ (katex, @svgdotjs/svg.js) are only needed at build time, so they are devDependencies.
  • dependencies is meant for the Node CLI (src/cli.ts). hyphen is a dependency because the CLI loads the patterns of languages other than English at runtime (require("hyphen/<lang>")); only hyphen/en is bundled.

TypeScript ​

  • All tsconfigs use module: EsNext and moduleResolution: Bundler, which the hyphen/en-style subpath imports need. Vite does the transpiling; tsc is only used for type checking (noEmit).
  • Relative imports in the source include the .ts extension.
  • Self-imports of "latex.js" (from cli.ts, the tests and the docs) resolve like this:
    • type checking: customConditions: ["latex.js-source"] maps them to src/index.ts. This is set in the root tsconfig and inherited by test/ and docs/.vitepress/.
    • runtime (Node, tsx, Vite/VitePress): they resolve through exports to dist/, so a build is needed.
  • Editors pick the nearest tsconfig.json in the file's parent folders. For docs/components/* that is the root tsconfig, which only includes src/. So there, "latex.js" resolves to dist/types/index.d.ts (generated by unplugin-dts), and the editor only sees the types after a build.
  • Two TypeScript versions are installed:
    • typescript 7.x: the compiler (tsc) for type checking, also run by vite-plugin-checker during vite build.
    • @typescript/typescript6 6.x: TypeScript 7 has no JavaScript compiler API, so the tools that need it (unplugin-dts, vue-tsc) use this one. It depends on @typescript/old (a real typescript@6), whose own tsc bin collides with the one of TypeScript 7; the prepare script re-links node_modules/.bin/tsc to TypeScript 7. If npx tsc -v doesn't print 7.x, run npm run prepare.
  • .vue files are type-checked by node lib/vue-tsc.cjs (part of npm run typecheck), which runs vue-tsc with TypeScript 6. Plain npx vue-tsc crashes, and plain tsc ignores .vue files.

Published Types ​

  • unplugin-dts emits src/**/*.ts to dist/types/**/*.d.ts (entryRoot: "src"), plus a CommonJS copy as *.d.cts next to them. exports in package.json references them directly: import → dist/types/index.d.ts, require → dist/types/index.d.cts. The package is "type": "module", so a CommonJS consumer can't use the .d.ts files (TS1479 under node16).
  • Published types must not reference devDependencies (peggy, svg.js, …): consumers don't have them. Mark internal members that would leak such types with /** @internal */ (stripInternal is on).
  • Mixins in src/generator/ that are constrained by an intersection of mixin APIs must declare override reset(), even if trivially. Otherwise the emitted .d.ts declares reset as a property, and Generator's override reset() fails with TS2425.
  • When you change the build or the public API, run npm run build && npm run test-int, see Integration Tests.

Conventions ​

  • 4-space indentation (see .editorconfig). Match the style of the code around your change.
  • The KaTeX stylesheets are generated by lib/katex-css.mjs (part of the build) from the installed katex: dist/fonts/katex.css holds only the @font-face rules, and dist/css/katex.css the rest, importing them. Don't add a src/css/katex.css. @font-face is ignored in a shadow DOM, so pages that show the output in one (like <latex-js>) load fonts/cmu.css and fonts/katex.css into the page itself.
  • When updating katex, check src/css/base.css against KaTeX's class names (e.g. .mathnormal, which used to be .mathdefault), and look at the math screenshots.
  • When you change the behavior or the API, update the documentation in docs/ and the README.md.
  • Don't commit anything from dist/, website/ or docs/.vitepress/cache/.
